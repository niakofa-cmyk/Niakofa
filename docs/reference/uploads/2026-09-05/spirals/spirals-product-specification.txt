🌍 In African traditions
Across a number of African artistic and spiritual traditions, the spiral can relate to life, creation, movement, transformation, ancestry, regeneration, and cyclical time.
For example:
* Asante/Akan traditions: Spirals appear extensively in goldweights, regalia, architectural decoration, and other objects. One British Museum record specifically identifies elaborate spirals in Asante material culture as a symbol of birth, creation, and regeneration.
* Kongo traditions: Spiral compositions can have a much deeper cosmological meaning. Smithsonian research describes Kongo spiral imagery as potentially referring to the journey of the dead to the ancestral realm and their return as newborns—essentially a cycle connecting life, death, ancestors, and rebirth.
* Igbo/Nigerian visual systems: In nsibidi, a graphic communication system, the spiral has been interpreted as representing a journey, while also suggesting the sun and eternity.
* Other Central African traditions: Spiral forms can occur in objects associated with healing, ritual, initiation, divination, and spiritual power. For instance, the Smithsonian documents spiral-form Yaka amulets used within healing traditions.
So, in an African context, the spiral can be understood as a visual expression of:
Birth → life → death → ancestors → renewal → life
rather than simply being a decorative shape.
🌀 Why the spiral is especially powerful
The spiral has an interesting quality that a straight line doesn't: it moves while returning around a center.
That makes it a natural visual metaphor for things such as:
* Cycles of life
* Generations
* Ancestral connection
* Birth and rebirth
* Growth and evolution
* Journeying
* Movement between physical and spiritual worlds
* Creation
* Time
* Transformation
* Returning to one's center/source
The center is particularly interesting. A spiral can be interpreted as movement outward from a source or movement inward toward a center.
That makes it particularly useful as a symbol of origin and return.


Remembering where we came from while continuing to evolve.
It can represent the idea that history isn't simply behind you. The past, ancestors, present life, and future generations are connected.
That interpretation is particularly compatible with the Kongo example, where the spiral was understood in relation to movement between the living and ancestral realms.

I think “Niakofa Spirals” is potentially much stronger than “Niakofa Circles”—especially given the cultural meaning you’re considering.
The distinction is meaningful:
* Circles → unity, community, equality, wholeness, gathering, cycles.
* Spirals → growth, evolution, movement, ancestry, regeneration, transformation, journey, returning to center.
* Niakofa Spirals → suggests a community that is not merely connected, but continually growing and evolving.
For a brand like Niakofa, Spirals also creates a more distinctive visual identity. A circle is ubiquitous; a spiral can become a recognizable Niakofa-specific symbol/system.
My recommendation
Don't simply rename the existing Circles feature. Re-conceptualize it.
Think:
Niakofa Circles → people gather around a shared center.
Niakofa Spirals → people gather, connect, learn, grow, and move outward into increasingly meaningful relationships and experiences.
That gives the product concept more depth.
One potential concern: “spiral” can imply complexity, inwardness, or even instability in some contexts (“spiraling”), so the UX and visual language should make the intended meaning unmistakably growth + connection + progression.



NIAKOFA FORENSIC ERROR REPORT
Repository: niakofa-cmyk/Niakofa Baseline: latest main commit a16842afabbb7d3cfd6f80011b75a9693996457a — September 5, 2026. Reference: uploaded Circles desktop/mobile designs.
P0 — CRITICAL
* P0-01 — Nia/App boundary has enforcement gaps. Boundary checker validates import statements, but does not prove runtime HTTP traffic is exclusively through nia-proxy, does not inspect dynamic imports, aliases, generated JS, environment-level coupling, or network calls.
* P0-02 — Circle recording completion invokes AI summarization from the App API layer. audio-circles.ts contains generateAiSummaryInBackground() and invokes it after recording; this creates an architectural coupling point that must remain strictly proxy-mediated and independently kill-switchable.
* P0-03 — Nia memory/AI controls have historically had bypasses. Previous audit records identify memory endpoints bypassing the Nia kill-switch, demonstrating that the boundary has already experienced fail-closed gaps.
P1 — HIGH
* P1-01 — getActiveParticipants() has no database limit. Every active participant row is loaded for live-room operations. Large rooms can produce excessive DB, memory, serialization, and WebSocket workload.
* P1-02 — /audio-circles contains an N+1 query pattern. Each circle independently performs live-session, follow, participant, and host queries inside Promise.all(). A city with many neighborhood Circles can generate a large burst of concurrent database queries.
* P1-03 — Circle provisioning occurs during read requests. GET /audio-circles can create neighborhoods and Circle records before returning the response. This mixes read traffic with potentially expensive database writes and makes browse latency dependent on provisioning.
* P1-04 — Circle provisioning intentionally swallows failures. ensureCirclesForCity() logs and suppresses errors, allowing partially provisioned city state to appear indistinguishable from legitimate empty/partial Circle data.
* P1-05 — Host expiration is lazy. Abandoned sessions are not guaranteed to terminate at the 90-second boundary; expiration occurs when another request touches the session.
* P1-06 — Host failover has a concurrency race surface. Multiple simultaneous requests can enter expiration/failover logic, select/promote participants, update the session, and broadcast transfer events concurrently.
* P1-07 — In-memory WebSocket participant state is process-local. Circle signaling uses a Map<number, Set<number>>; multi-instance deployment requires shared presence/routing or guaranteed sticky topology.
* P1-08 — Legacy mesh WebRTC implementation remains in the application. audioCircleWebRTC.ts still creates raw RTCPeerConnection objects while the newer architecture specifies LiveKit as the media plane.
* P1-09 — Two media architectures increase regression risk. The repository simultaneously contains LiveKit media architecture and legacy mesh fallback. The documented fallback behavior must be made explicit and mutually exclusive at runtime.
* P1-10 — LiveKit fallback requirements are not equivalent to production certification. The repository specification requires real-device tests for camera failure, permission denial, network transition, reconnect, and two-device operation, but repository inspection cannot establish that those scenarios currently pass in production.
P1 — SECURITY / MODERATION
* P1-11 — Participant retrieval lacks an explicit hard ceiling. The UI presents bounded speaker/audience experiences, but server participant retrieval can return the entire active population.
* P1-12 — Moderation state depends on both DB state and in-memory WS state. Divergence between these sources can cause stale participant targeting, especially after process restart or multi-instance deployment.
* P1-13 — Automatic co-host promotion needs atomicity. Role promotion and host_id replacement should occur in one transaction with a single-winner constraint.
* P1-14 — Circle blocking/reporting requires cross-check testing against reconnect/rejoin flows. Block/report tables exist, but realtime authorization must remain synchronized with those persistent moderation records.
P2 — PERFORMANCE
* P2-01 — Circle list loading scales poorly with city size.
* P2-02 — Participant queries repeatedly join the users table.
* P2-03 — Host lookup is performed separately instead of being incorporated into the session query.
* P2-04 — Follow-state lookup is performed separately for every Circle.
* P2-05 — Promise.all() permits database query bursts rather than controlled concurrency.
* P2-06 — Lazy expiration can cause stale live-room metadata between requests.
* P2-07 — Background AI summary generation is fire-and-forget from the request lifecycle; retry/durability guarantees need to be explicit.
P2 — UX / REFERENCE MISMATCH RISKS
* P2-08 — The reference design is deeply Circle-specific. Renaming only visible labels to “Spirals” would leave routes, storage, APIs, types, tests, documentation, cache keys, and architecture named Circle.
* P2-09 — audio-circles remains the dominant product/API namespace. A Circles → Spirals transition therefore requires a deliberate compatibility/migration strategy rather than a UI-only rename.
* P2-10 — Reference speaker-limit choices and backend choices must remain identical. The repository exposes 4 / 8 / 12 / 18 / 24, with server enforcement documented separately.
* P2-11 — Mobile reference separates the participant room experience from the moderation/control experience. Any implementation that simply stacks the desktop panels vertically will not satisfy the reference interaction model.
* P2-12 — Reference hierarchy requires Host → Co-Host → Speakers → Audience. Backend role state must never permit UI-only role assumptions.
P2 — NIA AI SEPARATION
* P2-13 — Enforce Nia as a separate service boundary at runtime, not merely statically. Current architecture explicitly requires HTTP-only communication through nia-proxy.
* P2-14 — Nia must never become a dependency of core Circle availability.
* P2-15 — Circle recording must succeed even when Nia is disabled/unavailable.
* P2-16 — AI summary failure must never corrupt recording state.
* P2-17 — AI summary generation needs idempotency/retry protection.
* P2-18 — Nia kill-switch must gate Circle-triggered AI work independently of Circle recording/moderation.
* P2-19 — AI-generated Circle artifacts need explicit privacy/retention policy boundaries.
* P2-20 — Existing Nia architecture already requires DB-backed, transactional, broadcast kill-switch behavior; Circle integrations must conform to that contract.
