What was implemented well
BUG-15b (max_travel_miles at claim time): The check is in the claim route in requests.ts. Emergencies bypass it and the default is 15 miles. The final UPDATE is atomic (WHERE status = 'open'), so a race returns 409. bug-15b-15c.test.ts covers the over-distance, emergency and within-range cases. It also gained extras I didn't recommend: self-claim block, idempotent replay and sensitive-category trust gates.
BUG-15c (/checkin endpoint): nia-service/src/routes/checkin.ts exists and is better than the version I'd sketched. It fails closed if INTERNAL_SECRET is unset, validates input, checks the user exists before calling the model, and handles crisis-hub context. It uses Haiku instead of Opus, which is a sensible cost choice. A checkin.test.ts exists.
FK constraints: 0020_core_foreign_keys.sql and 0011_forensic_schema_hardening.sql exist.
CI: It runs the boundary check, ESLint with --max-warnings 0, typecheck, and backend tests against a PostGIS service. It also runs migrations and spatial integration tests. That's stronger than what I originally suggested.
Secrets: My scan found only placeholders (sk_live_... in .env.railway.example), no real keys.
Where the implementation falls short
Silent catches aren't fully gone. The docs say all 22 were replaced, but about 17 empty .catch(() => {}) remain in server code: 11 in community-exchange.ts, 1 in reports.ts, and 5 in nia-service (chat.ts, crisis-followup-worker.ts). Roughly 90 more are in frontend code. Some of this may be newer code, but the "✅ all done" claim is no longer true.
Distance check fails open. If the helper has no lat/lng on file, the check is skipped and the claim goes through. For a "hard server-side block" that's a loophole. Either require a location or return a clear "set your location" error. Also, the Community Pool code can write community_id to the user before the claim succeeds, so a failed claim can still change user data.
Non-constant-time secret comparison in checkin.ts. It uses secret !== INTERNAL_SECRET, while the rest of the repo (nia-service/src/lib/auth.ts) uses timingSafeEqual. Swap in the shared helper.
Prompt-injection surface in /checkin. requestTitle is user-authored text interpolated straight into the prompt. Cap its length and put it in a delimited block, since the output goes back to the user as Nia's voice.
notifType (BUG-15d) isn't provably complete. I count 62 push call sites but only 47 notifType references. The cleanest fix is to make notifType a required field in PushPayload, so the compiler enforces it instead of a doc.
Duplicate migration prefixes are wider than the forensic doc says. It flags only 0118, but 0009, 0052, 0059, 0063, 0079, 0119, 0121, 0122 and 0123 are also duplicated. As that doc says, don't rename applied migrations. Do confirm the runner's tracking handles it, and add a CI check that blocks new duplicates.
Recommendations
Fix doc drift. The action-plan checklist still shows unchecked boxes for tests that now exist, with duplicated lines. Keep one source of truth, or generate the status from CI.
Clean up the repo root. 53 tracked root files include one-off scripts (patch_*.py, fix_*_file.py, apply_nia_fixes.py, push_session14_niaproxy_rewrite.sh, encrypt_token.py) and many dated audit notes. Move them to archive/ or docs/, or delete them. Leftover scripts like encrypt_token.py invite accidental token handling.
Add a lint rule against empty catches. ESLint's no-empty-function, or a no-restricted-syntax rule matching .catch(() => {}), would stop this from creeping back.
Write down the rate-limit policy. The forensic doc already notes that the Redis fallback to local counters is a tradeoff. List which routes must fail closed (login, payout, Stripe-related) and implement that.
Finish the production gate. The live-environment items (Railway preflight, Stripe balance samples, the end-to-end webhook-to-payout test, CI on the deployed commit) can't be verified from GitHub, so they remain open.
