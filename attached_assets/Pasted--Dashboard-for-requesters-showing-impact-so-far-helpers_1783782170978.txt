No livable-wage floor tied to real cost of living — still a flat admin-set number.
Here's how I'd actually build it, using what's already in your codebase:
1. A per-county wage floor, not a global one
Right now getHourlyMinimumRate() in community-pool.ts returns one flat number for everyone. Replace it with a lookup on a new table:

county_wage_floors
  id, county_id (→ communities/civic table), hourly_minimum, 
  effective_date, source, set_by_admin_id
getHourlyMinimumRate(countyId) checks this table first, falls back to a state-level default, then a national default if neither exists. That fallback chain matters — you'll have counties with no data on day one, and helpers still need to get paid.
2. Where the number comes from
There's no free real-time API for cost-of-living — the honest options are:
* MIT Living Wage Calculator data (public, county-level, updated ~annually) — someone manually enters the number per county when it's released, since it's not a live feed.
* HUD Fair Market Rent as a proxy, which does have a queryable dataset, updated yearly.
* Or simplest to ship first: let county admins (you already have gov-sponsors and county-portal admin roles) enter their own number, sourced from whatever local data they trust. Crowdsourced-but-verified beats nothing.
I'd start with option 3 (admin-entered, one field in the civic portal) and layer in an MIT/HUD data import job later as a suggested default they can accept or override.
3. Pick one household assumption and say so
Living-wage numbers change a lot by household size (single adult vs. with kids). Pick single-adult-no-dependents as the baseline rate shown to everyone, and just be transparent about that assumption in the UI — don't try to ask every helper their household size, that's a privacy and complexity trap for little benefit.
4. Which county's rate applies
Use the request's county (where the work happens), not the helper's home county. That matches "local cost of living" and avoids a helper in a cheap county collecting a big-city rate for driving over the line.
5. Versioning so past payments don't shift
Store effective_date on each wage-floor row. When payHelperFromPool calculates a payout, it should use the rate that was active at job completion time, not whatever the current rate is — otherwise a rate update could retroactively change what someone thought they earned.
6. Surface it, don't bury it
Show the local minimum on the helper dashboard ("Your county's guaranteed minimum: $X/hr") so it's a visible promise, not a hidden calculation — that's what makes "livable wage" feel real rather than a marketing line.
That's the whole loop: county-scoped table → admin-entered (with room to later automate from public data) → applied at the request's location → locked in at completion time → shown transparently to helpers.
