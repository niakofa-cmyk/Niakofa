Also But you're right that something was still causing disappearance — I found it, and it's a different bug class. I swept every place the API joins to the users table and checked each one against which user-referencing columns are actually nullable. An INNER JOIN against a nullable column is a landmine: if the referenced user is gone, the entire row silently drops out of the query results — nothing was deleted, but it vanishes from whatever screen displays that query. That matches "disappearing while using the app" even better than a delete would, since there's no error, no toast, it just isn't in the list anymore.
Two real hits:
* audio-circles.ts, recordings archive — this is a direct regression from round 1: host_id is now nullable (my fix), but this query still used INNER JOIN, so a completed circle recording would vanish from the archive the moment its host deleted their account.
* requests.ts, admin hardship queue — requester_id turns out to have no foreign-key constraint at all, so nothing ever protected it; a request could silently drop from the pledge-forgiveness queue the same way.
Both are patched (INNER JOIN → LEFT JOIN) in the download above, with a README explaining exactly what's fixed, how to apply the patches, which other inner-joins I checked and ruled safe (they join on columns that still cascade-delete, so no orphan is possible there), and one real gap I found but didn't rush a fix for — requests.requester_id/helper_id still have zero DB-level enforcement, which is the structural root of this class of bug and deserves its own careful migration rather than a quick patch.

The root cause of the "disappearing data" pattern got found and fixed properly, not patched one screen at a time. It turned out to be one underlying behavior: whenever a query's parameters changed — switching modes, changing a filter, or (critically) your GPS coordinates updating as you move, since raw lat/lng was going straight into cache keys and changing on nearly every render — the data-fetching library would show nothing for one render before the new data arrived. That's the "flicker to empty" you were seeing. It's now fixed at the root: every query in the app defaults to holding its last good value during a refresh, GPS-driven map queries are debounced so they don't regenerate a new cache key on every tiny movement, and there's now a fallback that also survives an outright failed refetch, not just a slow one.
Real permanent data loss was also found and fixed at the database level — and this is the more serious one. Three tables (civic needs, Audio Circle sessions, heritage stories) had a foreign key set up so that deleting one person's account would silently delete shared community content — a civic need someone else had already claimed and completed, an entire Audio Circle conversation with everyone else's history in it, a heritage recording. That's true, permanent, unrecoverable data loss, not a display glitch — and it's fixed now to match the safer pattern already used everywhere else in the same tables.
One honest caveat, stated plainly in the fix itself: this only changes what happens on deletions from now on. If any accounts were deleted before this fix shipped, that content is already gone and isn't recoverable from the database — only from a backup taken before the deletion, if one exists. Worth checking your Railway backup retention window covers that possibility.
One more thing surfaced this round that's worth knowing about, even though it's not app data: the local development environment's own git history had gotten disconnected from the real project history at some point — a different, more alarming-sounding kind of "data missing" that turned out to be fully recoverable (nothing was actually lost, it was safely reset to match the real history rather than force-pushed over it).
