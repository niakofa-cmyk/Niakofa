🔴 Critical — found while tracing the data source
GET /requests has no auth and leaks exact home addresses once a request is claimed or completed.
The map screen itself only calls GET /requests/nearby, which is always status='open' and correctly fuzzes coordinates by ~100m before sending them to the browser. Good. But while tracing that fuzzing logic I found its sibling endpoint, GET /requests (the general list — used by the Community feed and Helper Dashboard history), has:

no requireAuth middleware at all — anyone, logged in or not, can call it directly
fuzzing applied only when status === "open"; for claimed/en_route/completed rows it returns the exact, unfuzzed lat/lng, plus the requester's real name, on the theory that "these already belong to the helper/requester relationship" — but there's no check that the caller is that helper or requester.

Anyone can hit /requests?status=completed and get back a list of real names tied to exact home coordinates. This isn't a map-rendering bug, it's the endpoint one tier below the map, and it's the more serious finding here. Recommend: require auth on this route and apply the same explicit requester/helper/admin ownership check that GET /requests/:id already correctly uses (that pattern already exists in your codebase — it just wasn't applied here too).
🟠 High — real bugs in what you're looking at right now
1. Isolated open requests can become invisible on the map.
The cluster layer only renders two things: cluster bubbles (filter: ["has", "point_count"]) and cluster-count labels. Mapbox's clustering GeoJSON source also emits unclustered individual points for any request that has no neighbor to group with — but there's no layer rendering those. Individual React <Marker> pins only take over above zoom 12 (showIndividualMarkers = mapZoom > 12). Anyone landing on the map below that zoom — which includes every user without GPS permission, since the IP-location fallback defaults to zoom 11 — sees a completely blank map for a lone request anywhere near them, emergency or not, until they manually zoom in. For an app whose whole pitch is "urgent local help, visible right now," that's a real gap, and it disproportionately hits the exact people least likely to have already granted location access.
2. A helper going online doesn't appear live on anyone else's map.
The backend correctly broadcasts a helper_online WebSocket event with the new helper's full {id, name, lat, lng} the moment someone toggles "Go Online." But in map.tsx, the handler for that event does nothing with the payload — it just calls setWsConnected(true), which is already redundant. Compare that to helper_offline, which correctly removes the marker instantly. So helpers vanish from the map in real time when they go offline, but don't appear in real time when they come online — they only show up after the next full query refetch. That's a one-line asymmetry with a real UX cost for a "real-time help network."
🟡 Medium
3. Helper live-location isn't fuzzed at all — inconsistent with your own privacy design.
GET /helpers/online returns lat: h.lat!, lng: h.lng! — full precision — to any authenticated user within radius, gated only by the helper's privacy_live_location opt-in setting. Meanwhile, requester coordinates get deliberate ~100m jitter (documented, deterministic, well-reasoned). A helper who opts into "share my live location" almost certainly expects an approximate dot, like a rideshare driver icon — not their exact GPS fix, which is home-address-precision if they went online from home. Worth fuzzing this the same way, or at minimum documenting clearly to helpers what "opt in" actually shares.
4. RequestMarker has an unused safety feature.
The component accepts skillMatch and outsideServiceArea props with a comment referencing a "Local-First Dispatch" design (dashed ring for requests outside a helper's service radius) — but map.tsx only ever calls <RequestMarker request={r} />. Neither prop is ever passed, so this visual indicator is dead code. Either wire it up (compute it from the helper's service_radius_miles/max_travel_miles vs. distance, which the map already fetches) or remove the unused props.
