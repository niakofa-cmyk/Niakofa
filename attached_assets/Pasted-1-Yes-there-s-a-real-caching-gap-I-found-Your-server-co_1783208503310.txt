1. Yes — there's a real caching gap I found
Your server correctly sends "don't cache me" headers on index.html:

js
if (filePath.endsWith("index.html")) {
  res.setHeader("Cache-Control", "no-cache, no-store, must-revalidate");
  ...
}
But /sw.js (the service worker file itself) is not covered by that check — it falls through express.static's defaults, which don't set an explicit Cache-Control header at all. Browsers are supposed to re-check a service worker script periodically regardless of caching, but the spec allows them to go up to 24 hours before forcing that check if no explicit no-cache header is present. That matches exactly what you're describing: you ship an update, but your browser (or a teammate's) keeps running the old service worker for a while, which means it's still using its old cache-first logic and old cached JS bundles.
Fix: add the same no-cache, no-store, must-revalidate headers to /sw.js specifically, not just index.html. That's a one-line addition to the existing setHeaders function.
There's a second, smaller gap: the service worker has no controllerchange listener in the app code, so even once a new service worker does take over, a tab that's already open won't auto-reload to pick up the new JS — the user has to manually refresh. Worth adding a small "New version available — tap to refresh" prompt.



2. Nia AI's default is correct in the code — but that's not the same as its current state
I traced this all the way through, and the code is actually doing the right thing:
* The database migration explicitly seeds nia_enabled = 'false' on setup.
* Every place that checks it (nia-proxy.ts, nia-service/db.ts) is fail-closed: a missing row, a DB hiccup, or any value other than the literal string "true" all resolve to disabled. There's even a comment noting this was previously fail-open as a "defense in depth" measure and was deliberately changed because that was unsafe.
So "disabled by default" is genuinely how the code behaves on a fresh install.
If you're seeing it enabled right now, that's almost certainly because someone (an admin, or a prior test) explicitly flipped the toggle to "true" at some point — and that setting lives in the database, not in the code or the build. That's intentional: it means a redeploy doesn't silently wipe your admin settings. But it also means "disabled by default" only applies to a fresh database, not to an environment where the toggle was already touched once.
To check the real, current, live state (not something that can be stale from a cached build), the source of truth is the system_settings table's nia_enabled row — there's already an admin analytics endpoint reading exactly that. If it says "true", someone turned it on and it needs to be explicitly turned back off; that's not a caching bug, it's just how the toggle is supposed to persist.
Bottom line
* The "stuck on old build" feeling is very likely real, caused by /sw.js missing a no-cache header — easy, concrete fix.
* Nia being enabled is very likely a real toggle state in your database, not a stale build — check the DB value directly rather than assuming code is misbehaving.
