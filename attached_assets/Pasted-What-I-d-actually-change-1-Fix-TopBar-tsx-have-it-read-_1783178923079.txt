Good news and bad news. I dug through the actual repo (not memory), and here's what I found.
The good news: your UX spec is already built, almost verbatim.
NiaDrawer.tsx / NiaFab.tsx already implement exactly what you described:
* Dormant orb: opacity: dormant ? 0.42 : 1, filter: grayscale(75%) brightness(0.55), no aura/heartbeat/shimmer/particle layers when dormant, crescent glyph instead of the "N" (lines ~197–351)
* Same anchor position, drag disabled when dormant (drag={enabled && !dormant})
* Tap shows a 3-second tooltip instead of opening the drawer (handleClick, ~line 1430)
* Wake-word listening explicitly disabled when dormant: useVoiceWakeWord({ enabled: (enabled ?? true) && !dormant, ... })
So the frontend "sleeping, not dead" design is not the problem.
The actual bug: the killswitch has two independent enforcers, and they disagree.
Nia's chat traffic gets checked in two places:
1. artifacts/api-server/src/routes/nia-proxy.ts (isNiaEnabled()) — fail-closed: missing row, wrong value, or DB error all resolve to false (disabled). This one's correct.
2. artifacts/nia-service/src/lib/db.ts (its own separate isNiaEnabled(), line ~609–623) — fail-open:

js
_niaCachedEnabled = row.rows.length === 0 || row.rows[0].value !== "false";
...
} catch {
  _niaCachedEnabled = true; // fail open
}
Missing row → enabled. DB error → enabled. Anything other than the literal string "false" → enabled.
The comment justifies this as "defense-in-depth backstop — the proxy already blocks disabled traffic." That assumption is the hardwiring problem you're describing: it treats nia-service's own gate as decorative, so it was written to default to on.
Why the row can actually be missing: only api-server's migration (0018_system_settings.sql) seeds nia_enabled = 'false'. nia-service's own migrate.sql creates the same table (CREATE TABLE IF NOT EXISTS) but never inserts that seed row — it just assumes api-server already did. Your own run-migrations.mjs even has a recovery block explicitly written for the case where "0018_system_settings.sql" is marked as applied but the table was never actually created — meaning this exact failure mode has already bitten you once.
Put together: if nia-service ever reads system_settings before that row exists (race on first boot, a redeploy that resets the DB, migration tracker drift), nia-service defaults Nia to on, independent of whatever the admin toggle or api-server says.
Fix: make nia-service's check match api-server's — fail-closed, no exceptions:

js
_niaCachedEnabled = row.rows.length > 0 && row.rows[0].value === "true";
...
} catch {
  _niaCachedEnabled = false; // fail closed — a broken read must never enable Nia
}
