/stripe/payment-intent skips requireApproved. Every other money-moving route (payout, connect/onboard, wallet/cashout) explicitly adds requireApproved on top of requireAuth to block suspended/banned users — with comments noting this was a previous audit fix. payment-intent (creating a charge as a requester) does not have this check. It's lower severity since the user is paying money rather than receiving it, but a suspended/banned account can still charge a card through your platform. Worth a decision: is that intentional (e.g. so users can still repay pledges even while under review) or an oversight?
No automated tests for the actual money-moving logic. I found exactly one payment-related test file (repayment-dates.test.mjs), which covers date math, not money. The webhook handler, payment-intent creation, payout verification, and wallet cashout flow — the highest-stakes code in the app — have zero test coverage I could find. Given how much idempotency/locking logic is packed into these routes, that's the biggest risk in the payments surface: a refactor could silently break the double-payment guards with nothing catching it.
Minor: getStripeConnectStatus refresh — the live Stripe status sync in /stripe/connect/status/:userId swallows errors with just a logger.warn and falls back to stale DB data. Fine for UX, just means a truly stale/disabled Connect account could look "enabled" to the UI for a while.
