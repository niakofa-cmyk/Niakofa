# Heading-Up Fix — What Was Broken and What I Changed

## Why it was jumping (the actual root causes, verified in code)

I read `useDeviceHeading.ts`, `useMapOrientation.ts`, and `map.tsx` in full.
North-Up works because it's a one-time `bearing: 0` animation. Heading-Up
was broken for four separate, compounding reasons:

1. **Competing animations.** Every single compass event (often 20–60 times a
   second) triggered a brand-new `map.easeTo({ bearing, duration: 300 })`.
   Mapbox starts a fresh tween on every call — so animation #2 interrupted
   animation #1 mid-flight, which interrupted #3, forever. That interrupt-
   and-restart cycle *is* the visible jump. It's not a rendering glitch, it's
   dozens of animations fighting over the same camera property.
2. **A magnetometer alone, with no vehicle in mind.** The old code used
   *only* the phone's compass. Magnetometers are notoriously wrecked by
   nearby metal — which describes the inside of a car pretty well. Every
   real navigation product (Google Maps, Waze, Apple Maps) blends the
   compass with GPS course-over-ground once you're moving, specifically
   because of this. Niakofa's `AppContext` was already computing a GPS-
   derived heading and speed for the "my location" dot — it just was never
   connected to the map's orientation system.
3. **Double, competing sensor listeners.** Both `deviceorientationabsolute`
   and `deviceorientation` were registered at once. On Android devices that
   fire both, you get two different heading values racing each other.
4. **No screen-orientation compensation and no smoothing.** Rotating the
   phone (or the OS auto-rotating) could snap the raw `alpha` reading by
   90–270° with no correction, and raw sensor noise (±2–8° is normal) went
   straight into state with no filtering.

None of this needed a rewrite of your map — it needed the *heading pipeline
feeding* the map fixed. That's what these five files do.

## Files in this package

| File | What it does |
|---|---|
| `lib/heading-math.ts` | Shared, correct circular-angle math (shortest-arc smoothing, weighted circular mean, capped-step interpolation). Every heading bug traced back to plain arithmetic breaking at the 359°/0° wrap — this centralizes the fix. |
| `hooks/useDeviceHeading.ts` | Same public API as before, but: latches onto one sensor source instead of racing two, compensates for screen rotation, and smooths + throttles output. |
| `hooks/useFusedHeading.ts` | **New.** Blends the compass with GPS course-over-ground, weighted by speed — compass dominates when you're standing still (compass is more responsive there), GPS dominates once you're walking/driving (where it's far more stable). This is the "out of the box" fix — it's the same approach professional turn-by-turn nav uses. |
| `hooks/useMapOrientation.ts` | Replaces "new `easeTo` per sensor event" with a single `requestAnimationFrame` loop that continuously steps the camera toward the current target heading at a capped angular speed. One animation driver, never competing with itself. Also detects manual map rotation (`rotatestart`) and pauses auto-follow instead of fighting your fingers — with a "Resume Compass" button to hand control back, matching how Google Maps/Waze behave. |
| `pages/map.tsx` | Wiring only: swaps `useDeviceHeading` for `useFusedHeading` (fed with `myLocation.heading`/`.speed`), destructures the new `followPaused`/`resumeFollow` values, and adds the "Resume Compass" button next to the existing toggle. |

## How to apply

Drop these into the matching paths under
`artifacts/pay-it-forward/src/`:

```
src/lib/heading-math.ts                (new)
src/hooks/useDeviceHeading.ts          (replace)
src/hooks/useFusedHeading.ts           (new)
src/hooks/useMapOrientation.ts         (replace)
src/pages/map.tsx                      (replace)
```

Nothing else needs to change — `OrientationToggle.tsx` and `TurnArrowHUD.tsx`
were fine as-is and aren't touched.

## "Something out of the box" — where I'd take this next

You asked for more than a bug fix, so here's the ambitious version, roughly
in order of "biggest win for the effort":

1. **Predictive dead-reckoning between GPS fixes.** GPS position/course
   typically updates once a second. Waze-grade nav apps interpolate the
   puck's position and bearing *between* fixes using the gyroscope
   (`devicemotion` rotation rate) integrated over that second, so the arrow
   turns smoothly through a corner instead of snapping once a second. This
   is a natural next layer on top of `useFusedHeading` — same file, add a
   gyro-integration term.
2. **Speed-adaptive camera.** Real driving nav pulls the camera back and
   flattens pitch at highway speed, and zooms in/pitches up at walking
   pace or at intersections. `myLocation.speed` is already available —
   this is a small addition to `useMapOrientation` (or a sibling hook)
   that maps speed → target zoom/pitch, eased the same way bearing is now.
3. **Lane-level guidance using Mapbox Directions' `bannerInstructions`.**
   You already have `TurnArrowHUD.tsx` and a routing endpoint
   (`useGetRoute`) — pulling maneuver-level turn data would let Niakofa show
   "turn right in 200 ft" the way dedicated nav apps do, not just a route
   line.
4. **Crowd-sourced hazard/traffic overlay from helper GPS tracks.** You have
   every online helper's live position and speed already streaming over the
   WebSocket. Aggregating sudden speed drops across many helpers on the same
   road segment is literally how Waze detects live traffic jams and
   hazards — and Niakofa already has the raw data stream for it, uniquely
   tied to real people already out driving for help requests.

Items 1–2 are small, contained additions to what's now in this package.
Items 3–4 are bigger, genuinely differentiating features — 4 in particular
would be a real "nobody else's community app does this" capability, because
it rides on data Niakofa already collects for other reasons.
