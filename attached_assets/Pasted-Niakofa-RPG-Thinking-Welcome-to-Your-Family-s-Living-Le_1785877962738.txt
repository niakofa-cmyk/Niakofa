Technical Architecture
Since I've looked through your app structure, I would not build this as a separate codebase. I'd layer it onto the existing Niakofa architecture with a new legacy feature module:

Niakofa App

├── Authentication
├── Family Tree
├── Family Vault
├── Stories
├── Timeline
├── Notifications
├── Maps
├── AI Services
└── Legacy Module
      ├── Legacy Home
      ├── Story Engine
      ├── Quest Engine
      ├── Character Engine
      ├── Timeline Engine
      ├── World Map
      ├── Achievement Engine
      ├── Inventory
      ├── Family Events
      └── AI Narrator

The Legacy Module doesn't replace existing features—it orchestrates them. When a user adds a story, photo, interview, family member, or landmark anywhere in the app, those existing features emit events that the Legacy Module consumes to regenerate quests, dialogue, achievements, and world state.


The Key Innovation is World Regeneration.

Every new contribution changes the experience:
* A newly discovered ancestor unlocks a new playable chapter.
* A recorded oral history creates fresh dialogue and side quests.
* A tagged family landmark expands the exploration map.
* A restored photo reveals collectibles and historical context.
* A newly connected cousin enriches everyone's shared family world.
That means two sessions of the game are never exactly the same, because the family's history is continuously growing.

In that sense, Niakofa doesn't contain a game—the family's legacy is the game, and the app continually transforms that legacy into an evolving, collaborative experience that encourages preservation, discovery, and reconnection


1. Spec a minimal Family Vault schema + completeness API (people, relations, events, stories, places, consent).
2. One vertical slice: “Play as [Person] — Chapter 1 from earliest event.”
3. Wire achievements that only unlock vault prompts and reconnection actions.
4. Use Nia as coach/narrator with strict grounded prompts.
If you want to go further next, we can draft:
* the data model (tables / OpenAPI shapes aligned with existing lib/db + griot patterns),
* the readiness score rules,
* and a Phase 1 chapter state machine that stays honest to user data.
