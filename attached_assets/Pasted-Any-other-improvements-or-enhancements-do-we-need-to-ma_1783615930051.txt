This is a genuinely different kind of feature than what Niakofa has today, so let me be straight about the gap before getting into recommendations. Right now the "map" in this app is a local Mapbox view for hyperlocal matching — helper markers within a radius, in one county. What you're describing — a living connection point for the African Diaspora worldwide — is a different layer on top of that, not a bigger version of the same thing. Worth building as its own view, not a zoomed-out version of the local map.
1. A literal rotating globe is very achievable with what you already have
You're already on Mapbox GL JS for the local map. Mapbox supports a native globe projection (map.setProjection('globe')) — an actual 3D Earth with atmosphere, that you can populate with clustered pins for every diaspora community/user. This means you don't need a new mapping stack; you'd add a second view using the same library, just switched to globe projection with points across continents instead of a radius circle in one county.
2. Let heritage/lineage be self-described, not assigned
Add an optional (never required) profile field where people can self-identify — African American, Afro-Caribbean, Afro-Latino/a (Dominican, Puerto Rican, Colombian, Panamanian, Brazilian, Cuban, etc.), Afro-European, or continental African by country/ethnic group. This powers:
* Discovery ("find others who share your roots" nearby or globally)
* Optional community/affinity groups
* Culturally-relevant event surfacing (Juneteenth, Windrush Day, various national Emancipation Days, Carnival, etc.) Keep it opt-in and private-by-default — this is identity data people should control, not something inferred or required.
* Separate "connection" from "cross-border money movement"
* This is the most important sequencing decision. Diaspora discovery, storytelling, and connection (a global map of who's out there, a "roots" storytelling/oral-history space, a diaspora business directory) can launch relatively fast. Actual cross-border Pay-It-Forward payments are a much bigger lift — every country has different remittance law, KYC/AML requirements, and currency handling, and your background-check/trust-tier system is built around US verification providers that don't cover Nigeria, Jamaica, Brazil, etc. I'd strongly recommend:
* Phase 1: global map + cultural connection + storytelling (no money crossing borders)
* Phase 2: pick 2-3 pilot countries/diaspora hubs with legal review before extending real PIF payments internationally
* Language is a real lever here, not just a nice-to-have You already have Spanish support in Nia AI. Given the Diaspora you're describing, French (West/Central Africa, Haiti), Portuguese (Brazil, Angola, Mozambique, Cape Verde), and Haitian Creole would cover a huge share of it. Swahili, Yoruba, and Amharic would extend reach into continental Africa specifically.

This turns the globe from a map of where people are into a map of where stories live, which is a much stronger emotional anchor for "staying connected to lineage" than pins alone.

A few implementation notes for when this hits the actual codebase:
Data model. This is a state machine on a stories table, similar in shape to the system_settings pattern you already used for the Nia kill-switch: status enum (recorded → transcribing → pending_review → ready → published), a visibility column defaulting to 'public' with 'private' as the explicit opt-out, and a release_at timestamp the recorder controls (nullable — "publish now" vs. scheduled). Translations live in a child table (story_translations: story_id, language, nia_draft_text, recorder_approved boolean, approved_at) so a story can have five language drafts in five different review states simultaneously.
Worker pattern. The transcribe/translate step is a good fit for an async worker like your existing payout-worker.ts / notification-worker.ts / anomaly-worker.ts — record lands, job queues, Nia processes, recorder gets notified their translations are ready to review. Keeps the recording UI snappy instead of blocking on transcription.

One edge case worth deciding now: if a recorder never comes back to review a translation, does the original-language audio/text still go public on the default public-by-default timeline while the translation stays pending? yes — the recorder's own words shouldn't be held hostage by an unfinished translation — but translations should probably show a "pending review" badge instead of the Nia draft until approved, so a Portuguese-speaking descendant never mistakes an unreviewed machine translation for the recorder's own words.
