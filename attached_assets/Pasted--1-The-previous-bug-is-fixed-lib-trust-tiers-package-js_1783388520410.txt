2. New bug: pay-it-forward test script is broken
json"test": "node --import tsx/esm --test src/lib/__tests__/heading-math.test.ts"
This update switched the test runner from vitest to Node's built-in node:test + tsx (documented in vitest.config.ts — vitest 2.x is blocked by the Replit package firewall). But tsx was never added to pay-it-forward/package.json's devDependencies — only expect was added. Result: node --import tsx/esm fails immediately with ERR_MODULE_NOT_FOUND: Cannot find package 'tsx', even though tsx sits in the pnpm catalog (^4.21.0) and other packages (scripts, nia-service) already use it.
Fix confirmed: add "tsx": "catalog:" to pay-it-forward's devDependencies, reinstall → all 19 heading-math tests pass.
3. api-server test suite: 12 failing Jest tests
Running pnpm run test in artifacts/api-server shows 2 failed suites / 12 failed tests out of 71. I traced these to two distinct causes — not a single bug:
a) One test fails only due to test-order pollution, not an app bug.
lifecycle.test.ts › "returns 403 when requester tries to claim own request" fails (gets 409 instead of 403) when the full suite runs, but passes when run in isolation. The route code itself is correct (it checks "is this your own request" before anything else). The test file's beforeEach uses mockClear() instead of mockReset(), which clears call history but not queued mockResolvedValueOnce() values — so leftover queued mock responses from an earlier test in the file leak into this one and shift its DB-response queue by one. This is a test-hygiene bug, not a production bug.
b) 11 tests in integration-lifecycle.test.ts fail even in isolation — traced to a gap in that test file's hand-rolled DB mock. Several real query chains in requests.ts are perfectly valid under real Drizzle/Postgres because they end directly on .where(...) without a trailing .limit() — e.g. the "max 5 active requests" cap check and the "PIF pledge cap" check. But this test's mock only wires a resolvable promise onto .limit() and .returning(); anything that awaits a chain ending on plain .where() gets back the mock object itself (not an array), and destructuring [activeCount] = ... throws, which the route's error handler turns into a 500. That single 500 on request-creation is why "Full Request Lifecycle" and its dependent assertions collapse.
c) One real behavior mismatch worth flagging separately: "enforces maximum limit of 100" expects GET /requests?limit=200 to return 400, but the actual route just silently clamps the limit to Math.min(limitParam, 500) — it never rejects an over-limit request with 400 at all. Either the test encodes an intended contract (reject over-limit) that was never implemented, or the cap was deliberately raised from 100→500 and the test wasn't updated. Worth a decision either way — right now the code and the test disagree about what "maximum limit" should do.
