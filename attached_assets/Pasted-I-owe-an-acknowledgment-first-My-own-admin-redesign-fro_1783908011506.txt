I owe an acknowledgment first. My own admin redesign from last round had a real bug in it: I'd declared some new state hooks after a conditional early return in the component. That's a genuine violation of React's Rules of Hooks — it would have thrown "Rendered more hooks than during the previous render" the moment an admin actually logged in, since the not-yet-authenticated render calls fewer hooks than the authenticated one. It was caught and correctly fixed by moving those hooks above the gate. Good catch — that's exactly the kind of bug that looks fine until the one specific state transition that breaks it.
This round also caught a real one of its own — and it's a good one. The new list view I mentioned last time reuses a shared request card component. Its "Accept" button was only safe because of which screen happened to reach it — the helper-mode bottom sheet only ever mounts when helper mode is already on, so the gate was implicit. But the list view has no such mount guard; anyone can open it in any mode. So the Accept button itself now checks helperModeActive directly, instead of trusting that whichever screen got there first would've already handled it. That's a good general principle worth restating: a safety check that only works because of how something is currently reached isn't a real safety check — the moment a second path reaches the same button, it's exposed.
On the map specifically: this round consolidated the Filters/Layers/Orientation/Recenter controls into one proper panel (using the same drawer component already used elsewhere in the app, not a new pattern), added a "Request Help Here" long-press/pill action tied to the exact point you're looking at, and caught two real regressions along the way — the new panel and the list-view's own FAB were both accidentally rendering underneath the bottom nav bar on notched phones, and the WebGL-fallback screen briefly lost its only way to post a request. All fixed, with the exact safe-area math now documented for whoever touches this next.
