What already differs between helper mode and requester view

GPS broadcast cadence adapts by role/state — this is the one thing already handled well: AppContext.tsx throttles location updates to 2s during an active request (either party), 15s when idle in helper mode, 30s otherwise, with a minimum-movement threshold before it'll even send (2m/3m/10m respectively). That's a real battery-conscious design.
The claim gate and "Best Match" card are helper-only (showBestMatch = bestMatch && ..., pickBestMatch() only runs if helperModeActive).
The bottom sheet of nearby open requests only renders {helperModeActive && ...}.
Both roles otherwise see the same map component with the same markers, same live-helper dots, same navigation UI.

A real bug I found while tracing this
On map.tsx, the "Best Match" card is rendered as:
<DispatchIntelligenceCard bestMatch={bestMatch} onAccept={handleClaim} onDismiss={...} isClaiming={...} />
But DispatchIntelligenceCard.tsx's actual component signature takes completely different props: requestId, requestTitle, requestCategory, onHelperAssigned, wsVersion — there's no bestMatch, onAccept, onDismiss, or isClaiming anywhere in that file. Two different features ended up sharing one component name — looks like the AI-dispatch-recommendation card (used elsewhere, e.g. on the requester's side to show them a recommended helper) and the map's "best open request for you" card got cross-wired. As written this either fails TypeScript compilation or renders with undefined props at runtime, meaning the flagship helper-mode feature (the thing that's supposed to say "here's the best task for you right now, tap to accept") is likely dead code in production right now. I'd fix this before anything else in this list — it's your core helper-mode differentiator and it's currently broken.
A real design gap: navigation UI isn't actually helper-only
request-active.tsx renders <NavigationOverlay> and <TurnArrowHUD> unconditionally to whoever is on that screen — there's no isHelper check gating them. That means a requester sitting at home waiting for their groceries gets turn-by-turn walking/driving directions, an "off-route, recalculate" banner, and — because speakEnabled={true} with no role check — spoken voice navigation announcements ("Turn left in 200 feet") on their own phone, for a trip they're not taking. That's not just visual clutter, it's actively confusing and drains battery/attention for no reason. This should be gated on isHelper.

That table is really the design principle: helper mode is a "navigate to a task" surface, requester mode is a "track my helper" surface. They're currently sharing one UI built for the first case and just handed to both.
Other things worth fixing or adding

Precise location before claim. Right now useGetNearbyRequests/useGetOnlineHelpers return exact lat/lng to anyone authenticated within 10 miles. Before a request is claimed, consider fuzzing the requester's pin (e.g., snap to nearest street block or 100m jitter) — full precision only needs to be exposed to the helper after they've claimed. Right now any browsing helper (or anyone who signs up) can see exactly where every open requester lives, whether or not they ever intend to help.
Offline/weak-signal handling. I saw a WebGL fallback (mapError state shows a list view), which is good, but there's no fallback for GPS dropping mid-navigation beyond the existing off-route banner — worth a "last known position, X seconds ago" indicator instead of the dot silently freezing.
Clustering at low zoom. With the taxonomy expansion from earlier (16+ categories), a busy area will get marker-dense fast. Worth adding pin clustering (Mapbox supports this natively) once request density crosses some threshold, otherwise the map becomes unreadable in denser cities.
Safety-timer visibility asymmetry. I noticed a SAFETY_TIMER_SECONDS = 1200 constant in request-active.tsx — worth confirming that a stalled/no-progress trip (especially for the sensitive categories from earlier: childcare, senior care) alerts both parties and not just internally, and ideally lets the requester one-tap contact support/emergency if their helper goes dark.
"Share trip" exists (handleShare) — extend it. Right now it's on the active-trip screen; worth also letting requesters share a live-tracking link with a third party (a classic rideshare-safety pattern) — valuable given some of these categories involve people alone with someone they've just met.
Heatmap/demand view for helpers, not just pins — a light heat layer of recent request density by category/time-of-day would help helpers decide where to go idle and wait, not just what to accept when something appears nearby. This directly supports "paid a livable wage" — helpers can position themselves in high-demand areas instead of waiting passively.
