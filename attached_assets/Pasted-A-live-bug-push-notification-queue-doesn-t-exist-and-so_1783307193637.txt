A live bug: push_notification_queue doesn't exist, and something polls it every 5 minutes
Every ~5 minutes since this deployment started, a worker runs SELECT id, user_id, title, body, data FROM push_notification_queue WHERE sent_at IS NULL ORDER BY created_at ASC LIMIT $1 and Postgres throws relation "push_notification_queue" does not exist. This has been failing continuously for hours in this log. Let me check the codebase for what's supposed to create that table.


Why this didn't break everything
Three of those six tables (nia_conversations, nia_memories, system_settings) are also defined in the separate, properly-running Drizzle migration pipeline (lib/db/migrations/) — so Nia's actual chat history, memory, and the nia_enabled killswitch are all fine. That's why every earlier round of this audit found those working correctly.
But three tables exist only in the dead migrate.sql: nia_knowledge, push_notification_queue, and nia_cost_log. Since nothing ever creates them:
* push_notification_queue — confirmed broken by your log. Nia's proactive pushes (ambient-presence-worker, general-checkin-worker, crisis-followup-worker) have been silently failing to queue since deploy.
* nia_knowledge — very likely broken the same way. This is what continuous-learning-worker writes to — the "Nia learns about the world and never forgets" feature has probably been persisting nothing.
* nia_cost_log — likely broken too. Anthropic API cost tracking has probably been recording nothing this whole time.
None of these are fatal — core chat doesn't touch any of the three — but three real features have likely been silently inert since launch.
The fix
I traced the exact boot sequence in index.ts and wrote a patch that calls runMigrations() once, before the server starts accepting traffic, wrapped in try/catch so a migration hiccup logs loudly instead of crash-looping the whole service (since core chat doesn't depend on these 3 tables). Tested against your latest zip — applies cleanly, is idempotent, and passes an esbuild syntax check.
