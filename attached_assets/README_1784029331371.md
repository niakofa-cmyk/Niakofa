# Fix: Audio Circles "disappearing" (and how to verify the rest of the DB)

## What was actually happening

It wasn't data loss in the sense of rows being deleted. It was **rows that
never existed in the first place** for anyone outside Fort Worth:

- Migration `0064_audio_circles.sql` seeded `audio_circles` rows for
  **Fort Worth only**, as a one-time `INSERT`.
- No other code path in the app ever inserted an `audio_circles` row again.
  `GET /api/audio-circles` is a pure read.
- `city_neighborhoods`, by contrast, **does** self-provision — the first
  time anyone asks for a city that isn't Fort Worth, `GET
  /community/neighborhoods` generates and caches it. Audio Circles never
  got that same treatment.

Result: any user whose city (from GPS, profile, or search) wasn't the exact
string "Fort Worth" saw **"No circles yet for {city}" every time, forever**
— while Fort Worth looked fine because of that one migration. That's exactly
what "the Circles disappear once you leave or refresh" looks like from the
outside: they were never durable to begin with for real users, they just
happened to render once if your city defaulted to Fort Worth.

(Separately, your earlier round already fixed the frontend flashing-empty
bug in `audio-circles.tsx` — a failed poll no longer clears the list. That
fix is good and still in place; it just wasn't the actual bug behind
circles never showing up for non-Fort-Worth users.)

## The fix (3 files)

1. **`migrations/0073_audio_circles_autoprovision_uniques.sql`**
   Adds two partial-unique indexes (`neighborhood_id`, and `city_key` where
   `neighborhood_id IS NULL`) so circle creation can safely use
   `ON CONFLICT DO NOTHING` instead of a race-prone `NOT EXISTS` check.
   Also de-dupes any pre-existing duplicate rows first (no-op on a clean DB).

2. **`routes/community-neighborhoods.ts`**
   Pulled the existing cache-or-generate logic out into an exported
   `ensureNeighborhoodsForCity(cityRaw, cityKey)` — same behavior as before,
   just reusable instead of trapped inside one route handler.

3. **`routes/audio-circles.ts`**
   `GET /audio-circles` now calls a new `ensureCirclesForCity()` before
   reading: it makes sure the city has neighborhoods (via the function
   above), then upserts one circle per neighborhood plus the city-wide
   circle. This runs on every request but is a cheap no-op once circles
   exist. Any failure is logged and swallowed — a hiccup shows "whatever
   already exists," never a 500, never blanks out prior data.

Once these three files are applied, a circle is created **once**, in the
database, the first time anyone asks for that city — and from then on it's
a normal permanent row. Refreshing, navigating away, switching modes, or
losing your connection can't make it disappear, because nothing reads from
memory or from a cache that resets — every read goes straight to Postgres.

## How to apply

1. Run the migration (`0073_...sql`) against your database — via your
   existing migration runner, or `psql $DATABASE_URL -f 0073_....sql`.
   ⚠️ Given the `patch_nia_migrations_never_run` file in your
   `attached_assets`, **confirm your migration runner actually executes on
   deploy** — that's a second, independent risk worth verifying: if
   migrations silently don't run in production, none of this (or any prior
   fix) is actually live.
2. Replace `artifacts/api-server/src/routes/community-neighborhoods.ts` and
   `artifacts/api-server/src/routes/audio-circles.ts` with the versions here.
3. Redeploy the API server.

## On the rest of the DB / "vanishing data" more broadly

I checked the areas you called out specifically:

- **Requests**: `requester_id` is `ON DELETE RESTRICT` and `helper_id` is
  `ON DELETE SET NULL` (migration `0070`) — a request survives account
  deletion by design now; it can't cascade-delete.
- **Users**: no schema path found where a user row auto-deletes another
  user's data.
- **Map**: `map.tsx` already uses React Query with `keepPreviousData`, so
  in-flight refetches don't blank the map while new data loads.
- **AppContext**: current user and active request are persisted to
  `localStorage` with rollback-on-failure, so a page refresh restores them
  instead of losing them.
- **Audio Circles**: the gap above — now fixed.

Given how many cascade-delete and empty-state bugs your `attached_assets`
history shows were already found and fixed (hub pledges, gov sponsors,
content/griot stories, requester cascade, duplicate constraints), I'd treat
"is the DB in good shape" as **mostly yes, with Circles being the one real
remaining gap** — not evidence the whole data layer is unstable. The
general pattern worth watching going forward: any feature with a
"seed once via migration" launch (like Circles was) needs a matching
runtime "ensure it exists" path, or it only ever works for whatever was
seeded.
