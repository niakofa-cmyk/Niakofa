communities.ts (public routes) — well-built, but leaks something it shouldn't
The stats endpoints (/communities, /communities/:id, /communities/default) are solid: correctly aggregated SQL, matches the same pool-health-ratio clamp logic used server-side for wage math, no auth required which is right for a transparency page.
But GET /communities/:id/ledger has a real privacy problem. It returns each entry's notes field, and that field is populated in community-pool.ts like this:
notes: `Pool fronted helper payment for: ${requestTitle}`
notes: `Guaranteed minimum for completed task: ${requestTitle}`
requestTitle is the free-text title a requester wrote for their own help request — and this app has categories like medical, senior_care, mental_health_peer, and legal_aid, so titles can plausibly contain things like a health condition, a domestic situation, or other personal detail. I confirmed this is actually rendered live: community.tsx's "Public Ledger" widget displays entry.notes directly to any visitor, no login required.
The comment at the top of communities.ts says these are "no sensitive user data" — but I checked whether request titles are exposed anywhere else in the app, and they're not: GET /requests (the browse endpoint) requires requireAuth. So this is a new, unauthenticated leak of previously-private user content, not a duplicate of something already public. I'd fix this before it goes further — either strip/generalize the note text for the public ledger (e.g. "Helper paid for a completed task" with no title), or require the requester to opt in to having their request title shown publicly.
Admin CRUD (admin-communities.ts + CommunitiesTab) — backend is solid, UI has real gaps
Backend: proper requireAuth + requireAdmin() + rate limiting on every route, input validation (name length, positive numeric target), and it correctly strips password/reset fields before returning a reassigned user. No complaints here.
Three real gaps in what the UI actually lets an admin do:

The "Default" badge is dead code. CommunitiesTab renders a badge based on c.is_default, but I checked the schema — communitiesTable has no is_default column, and the API never returns one. The actual default-community mechanism is a system_settings.default_community_id key (read in getDefaultCommunityId()), and there's no route or UI anywhere to set it — I searched, it's only ever read, never written outside a raw DB edit. So today, admins can create counties and reassign users into them, but can't control which county a brand-new signup lands in without touching the database directly. That's the one control that matters most for a multi-county rollout, and it's missing.
The health-percentage bar shown to admins doesn't match the number that actually drives pay. The backend returns pool_health_ratio clamped to [0.5, 1.0] (a depleted pool still shows ≥50%, matching the wage-multiplier floor). The CommunitiesTab component ignores that field entirely and recomputes its own ratio = Math.min(balance/target, 1) client-side — with no floor. So a pool at $0 would show 0% in the admin dashboard while the backend is actually paying helpers at the 50%-floor rate. An admin staring at that bar would misjudge how healthy a pool really is.
The "unassigned" legacy bucket is invisible. The API response includes unassigned: { pool_balance, member_count } — literally the count of users still stuck in the NULL bucket, which was the whole reason this feature existed. The UI never reads or displays it. Given the entire point of this release was "the old global bucket is a problem, get everyone into a real county," not being able to see that number in the one screen built for managing it is a real oversight.
