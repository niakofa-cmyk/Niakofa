Now, Circles — you were right to point at this specifically, and I found the actual cause. It's not a delete bug at all:
Circles (the permanent per-neighborhood/city "channel") were only ever created for Fort Worth, by a one-time data migration back when the feature launched. I checked every place in the codebase that touches that table — nothing else, ever, creates a circle for any other city. Type in (or have a profile set to) any city besides Fort Worth and you get "No circles yet" — permanently, not intermittently.

So if you'd searched into Fort Worth (the one city with real content) and then left a room or refreshed, you'd get silently switched back to your own city — which almost certainly has zero circles — and see an empty list where a second ago you saw several. Fixed both halves:
* The backend now auto-provisions a real, permanent circle for any city the first time someone looks it up, the same way Fort Worth was hand-seeded — so this stops being a Fort-Worth-only feature.
* The frontend now remembers the last city you were browsing across a refresh or a room exit, instead of snapping back to your profile default.

This is a genuine, serious bug

Found it, and it was a real one — an actual bug in my own original design, not a display glitch like the others this session.
Refreshing the page while hosting an Audio Circle fires the exact same API call as tapping "leave" — a browser refresh has no way to say "I'm coming right back" versus "I'm done." The original code treated any host leaving as permanent and immediately ended the whole session for everyone else in the room. That's the actual mechanism behind "leave or refresh and the circles are all gone" — it wasn't a caching flicker like the map/civic-needs issues from earlier rounds, it was the session genuinely, permanently ending.
The fix: a host leaving now starts a 90-second grace period instead of ending anything. Their spot in the room is held open; if they come back (refresh reloads the page, which rejoins automatically), they're picked back up as host with zero disruption to anyone else. Only if they don't return in time does the session actually end. The deliberate "End Session" button is a completely separate action and still ends things immediately, exactly as it should — this only fixes the accidental path.
I also want to flag something honestly: this exact code path — what happens when a host leaves — had no test coverage at all before this, despite being the single highest-consequence branch in the whole feature. I added two tests for it directly. That's a good general lesson for this codebase going forward: the more damage a code path can do if it's wrong, the more it deserves a test, regardless of how simple the logic looks.
