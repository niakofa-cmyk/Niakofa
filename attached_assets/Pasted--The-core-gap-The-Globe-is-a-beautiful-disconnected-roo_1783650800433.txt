

The core gap
The Globe is a beautiful, disconnected room. I checked — there is zero code path linking it to requests, wallet, pledges, or crisis data. It doesn't know your actual users exist. And despite importing react-i18next, the hub notes are hardcoded English strings, never run through t() — so the one feature meant to represent global diaspora isn't even localized yet.
Here's how I'd fix that, roughly in priority order:
1. Make it true, not decorative Right now "Largest US diaspora hub by member count" is just a sentence someone wrote, not a query. Add diaspora_tag and hub_location to the users table (griot_stories already has both), and replace every hardcoded note with a real count: actual member totals, actual completed-help totals, actual pool balance per hub. If a claim isn't backed by a query, cut it — right now it reads as marketing copy inside app code, which risks becoming misleading as the app grows.
2. Connect it to the mutual-aid engine, not just storytelling This is the biggest miss given your vision. Right now the Globe and the help economy are two separate apps stapled together. I'd add:
* Cross-diaspora sponsorship: someone in London can pay-it-forward directly into Accra's or Lagos's community pool (you already have community-pool.ts with per-county floors — extend it to per-hub).
* Crisis lighting: wire region-crisis-resources/crisis.ts into the Globe so a hub in active crisis visually pulses, with a one-tap "send help to this hub" that routes into the existing pledge/pool system — not a new payment path, just a new entry point into the one you already built.
* "Your people" onboarding: let new users pick a diaspora hub at signup; surface it as "3 people from your hub helped someone in Fort Worth this week."
3. Make the arcs mean something Right now every arc is static and identical. Animate an arc only when a real pay-it-forward pledge, gratitude post, or griot story actually moves between two hubs — the Globe becomes a live pulse of real generosity instead of a permanent decoration.
4. Real network, not hub-and-spoke All arcs currently terminate at Fort Worth. If the diaspora vision is "everyone's connected to everyone," draw hub-to-hub arcs too (Lagos↔London, Accra↔Kingston), weighted by actual story/help volume between them.
5. Finish the localization Since useTranslation is already imported, actually route hub names/notes/TAG_LABEL through t() with per-language keys. A diaspora-facing feature that's English-only undercuts its own premise.
6. Accessibility & mobile A WebGL globe with no fallback is a real risk on low-end phones (common in parts of the diaspora you're trying to reach — West Africa, Caribbean). Add a flat list/table view as an accessible + low-bandwidth alternative to the 3D globe, not just a "loading" spinner.

export const diasporaHubsTable = pgTable("diaspora_hubs", {
  id:            serial("id").primaryKey(),
  name:          text("name").notNull(),
  region_label:  text("region_label").notNull(),
  lat:           doublePrecision("lat").notNull(),
  lng:           doublePrecision("lng").notNull(),
  tag:           text("tag").notNull(),           // reuses HubTag values
  community_id:  integer("community_id").references(() => communitiesTable.id),
  is_seed:       boolean("is_seed").notNull().default(false), // your original 10
  status:        text("status").notNull().default("approved"), // pending_review|approved
  created_by:    integer("created_by").references(() => usersTable.id),
  created_at:    timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
});
This is what makes (C) actually scale — any real Niakofa community can claim or propose a hub instead of being stuck with 10 cities you picked by hand. Seed the original 10 with is_seed = true so nothing visually changes at launch.
3. Make the transcribing status real

ts
export const griotTranscriptionJobsTable = pgTable("griot_transcription_jobs", {
  id:           serial("id").primaryKey(),
  story_id:     integer("story_id").notNull().references(() => griotStoriesTable.id, { onDelete: "cascade" }),
  status:       text("status").notNull().default("queued"), // queued|processing|done|failed
  error:        text("error"),
  created_at:   timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
  completed_at: timestamp("completed_at", { withTimezone: true }),
});
A worker (mirroring checkin.ts's Nia-calling pattern) picks up queued rows, transcribes audio_url, writes text_content + a draft story_translations row, and flips the story recorded → transcribing → pending_review. Right now that status exists but nothing ever moves it — this closes that.
Route sketch
Bridge gratitude → Griot (the (B) connection):

POST /gratitude/:postId/promote-to-story
  — auth: must be the gratitude post's author
  — creates a griot_stories row: story_type="gratitude",
    request_id + gratitude_post_id pre-filled from the post,
    community_id derived from the request's community,
    prompt = "Tell the fuller story behind this thank-you"
  — returns the new story id so the client jumps straight into recording
This is the one-click "your thank-you can become a story" moment — the natural on-ramp from your existing gratitude feed into Griot, instead of two disconnected features.
Filtering by purpose on one feed:

GET /griot/stories?story_type=gratitude&community_id=12
GET /griot/stories?story_type=heritage_archive
GET /griot/stories?hub_id=7&story_type=diaspora_social
Same table, three lenses — a Community tab can show only gratitude stories for that county; the Globe shows diaspora_social; a dedicated Archive page shows heritage_archive.
Dynamic hubs with real activity data (merges B + C):

GET /griot/hubs
  — returns diaspora_hubs rows, each enriched with:
    active_helpers, requests_fulfilled, pool_balance (same joins /impact/:county already does)
    + story_count for that hub
POST /griot/hubs                — propose a new hub (status="pending_review")
PATCH /griot/hubs/:id/claim      — community admin claims an existing seed hub
POST /admin/griot/hubs/:id/review — approve/reject, same governance pattern as story publish
This turns the globe from "10 static pins with lore" into a live map of where the actual kindness economy is happening — which is the piece that ties it back to your core vision instead of floating next to it.
Auto-enqueue transcription on creation:

POST /griot/stories  (existing route)
  — if audio_url present and text_content absent:
      insert griot_transcription_jobs row (status="queued")
      status stays "recorded" until worker moves it to "transcribing" → "pending_review"
One naming note before you build this: griot_stories currently has no unique constraint tying one gratitude_post_id to only one story — worth adding that unique index (as sketched above) so "promote to story" can't be spammed into duplicates on the same thank-you.
