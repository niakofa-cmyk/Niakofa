# Niakofa — remaining cascade-delete fix (hub pledges)

## Where these go
- `lib/db/src/schema/hub-pledges.ts` → replaces the existing file
- `lib/db/migrations/0069_fix_hub_pledge_cascade_delete.sql` → run after 0068,
  same way (`psql $DATABASE_URL -f lib/db/migrations/0069_fix_hub_pledge_cascade_delete.sql`,
  or however your existing migration runner applies `.sql` files in this repo —
  it's additive/idempotent-safe, same shape as 0068).

## What this fixes
Migration 0068 (already applied) fixed three tables where `ON DELETE CASCADE`
was wrongly used on a content row's *owner* FK instead of `SET NULL`:
`civic_needs.posted_by_user_id`, `audio_circle_sessions.host_id`,
`griot_stories.author_id`.

`diaspora_hub_pledges.pledged_by` has the exact same problem and was missed —
it lives in a different schema file (`hub-pledges.ts`, not one of the three
already audited). A pledge row records real money moving between two
community hubs (a `"pledged"` status row is backed by an already-captured
Stripe payment). Deleting the pledging user's account should never delete
that record — it belongs to the *receiving* hub's crisis-relief history as
much as to the person who sent it.

## Is this actively losing data right now?
No — `routes/users.ts` already has `findBlockingPledges()`, and both the
self-delete and admin-delete routes refuse to delete an account that has any
pledge history. So this specific cascade was not firing through the app's
normal delete paths.

It's still worth fixing at the schema level rather than relying only on that
guard, because:
- The check-then-delete isn't wrapped in one transaction — a pledge created
  in the moment between the check and the actual delete would still be
  destroyed by the old `CASCADE` rule.
- Any future code path, or a one-off manual/admin SQL cleanup, wouldn't
  automatically inherit that same application-level check.
- It's the one remaining outlier vs. the pattern already established (and
  now consistently used) everywhere else in this schema.

## After this
I checked every other `.references(...)` in `lib/db/src/schema/*.ts` for the
same "cascade on a shared-content owner" shape and didn't find another one —
this was the last one. Tables like `request_helpers` (helper_id cascade) and
`hub_leaders` (user_id cascade) look similar at a glance but are membership/
role-assignment links, not content records, which is the same distinction
the project's own migration 0068 comments already draw — those are correctly
left as-is.
