Root cause of "You can only start a spiral from inside Fort Worth"

verifyCircleStartLocation() in circleLocationPolicy.ts compared the Mapbox-resolved city against the Spiral's city with strict string equality: resolved.cityKey !== expectedKey. Zero tolerance.

Fort Worth has several genuine enclave/exclave municipalities — Westworth Village, River Oaks, Westover Hills — that are legally separate incorporated cities but are completely surrounded by Fort Worth. A GPS fix at an address physically inside Fort Worth can reverse-geocode to one of these enclave names rather than "Fort Worth" itself, and the old exact-match check denied it outright, indistinguishable from someone genuinely in a different city.

On top of that, the denial response carried no information about what city GPS actually resolved to — { ok: false, reason, code } and nothing else — so there was no way for the UI to ever show "your GPS shows X, this Spiral needs Y."

What was fixed

circleLocationPolicy.ts:

Added citiesMatchForHost() — exact match still passes first; falls back to a narrow, explicitly-documented enclave alias table (currently just Fort Worth's three enclaves). This does not weaken city-level host fencing between genuinely different cities — Dallas GPS still cannot host a Fort Worth Spiral, verified by a dedicated test.
Both the allow and deny results now carry spiralCityKey/ spiralCityDisplay and, once a fix is resolved, resolvedCityKey/ resolvedCityDisplay/neighborhoodHint — so the UI can always render "GPS shows X, Spiral needs Y."
Added displayCityName() so denial copy says "Fort Worth", not "fort worth".
reverseGeocodeCircleStart() now also extracts a best-effort neighborhood hint from Mapbox's own neighborhood context feature.

circle-location.ts (POST /audio-circles/:id/location-check): now returns resolved_city_key/resolved_city_display/neighborhood_hint and a ready-to-render host_signal string on both allow and deny.

audio-circles.ts (POST /audio-circles/:id/start): the 403 response now also includes spiral_city_display/resolved_city_display, so even the actual submit-time denial (not just the preview check) can show the same "GPS shows X" context if the frontend chooses to surface it later.

On your neighborhood-GPS question

I checked the schema directly: city_neighborhoods (the table backing Downtown, East Fort Worth, etc.) has no lat/lng or geofence columns at all — it's a table of named content rows (name, emoji, description) scoped to a city_key, not real geographic boundaries. So a genuinely verified per-neighborhood host gate isn't something that exists to turn on — building one would mean authoring real boundary polygons per neighborhood, which nobody has done yet. I'm not going to claim to have built neighborhood-level geofencing that isn't backed by real data.

What I built instead, honestly scoped: a best-effort neighborhood hint surfaced from Mapbox's own reverse-geocode response, clearly presented as a hint ("near Downtown") rather than a verified gate. The actual host boundary — the thing that's enforced and tested — stays at the city level, which is the only geography Niakofa has real, verified data for today.

New: Verified GPS Host Signal (SpiralHostSignal.tsx)

The real UX bug I found that the uploaded package didn't mention: the "Host a Spiral" modal closes and submits before any location check runs — startRoom() calls setHostModal(null) immediately, then does the GPS capture and POST. So a user could fill out the whole form (title, topic, speaker limit, recording toggle) and only find out they're denied after submitting, via a generic toast.

SpiralHostSignal.tsx is a small on-demand widget wired into both:

The discovery page, right below the city search box — one check applies to the whole browsed city, since eligibility isn't per-Spiral.
The Host modal itself, so it's visible before filling out the form.

It deliberately does not auto-run on page load — requesting a fresh, high-accuracy GPS fix (enableHighAccuracy, maximumAge: 0) automatically would either force a permission prompt before the user asked for one, or silently do nothing for anyone who hasn't granted location yet. It shows a "Check if I can host in {city}" button; tapping it reuses the same server-authoritative /location-check route (never decides eligibility client-side) and renders the server's host_signal copy:

✅ "Verified: you can host in Fort Worth (near Near Southside)."
🔒 "Hosting unlocked in Fort Worth only. GPS shows Kansas City. You can still join."
