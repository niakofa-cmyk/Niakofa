Diaspora Globe-first redesign
This PR implements the recommended top-level architecture:

Diaspora → Globe → Hub → Action

Implemented
Replaces the crowded /diaspora landing dashboard with a Globe-first doorway.
Adds reusable DiasporaGlobeFirst with live Hub markers, search, compact Hub details, and mobile-friendly actions.
Globe markers represent durable Diaspora Hubs, not individual members.
Adds canonical Hub geography metadata: hub_scope, country_code, subdivision_code, display_name, and anchor_city.
Non-U.S. seed Hubs are now presented as country-level Hubs (Ghana, Nigeria, Brazil, Jamaica, Dominican Republic, United Kingdom, France, Canada).
U.S. seed Hubs are presented at state level (Texas, Georgia, California, New York).
Existing city anchor names/coordinates remain intact internally so neighborhood, Spiral, story, and presence aggregation does not lose its existing geographic relationship.
Hub search works across public Hub name, anchor name, region, country/state codes, and Hub type.
Hub selection exposes compact actions for Community, Connect, Spirals, Stories, and Community Pool.
Existing family, oral-history, Legacy, and full Globe routes remain underneath the new doorway.
Raw GPS continues to stay server-side because the page consumes the canonical authenticated /api/griot/village-pulse aggregate.
Architecture decision
The landing page is intentionally no longer a feature directory. Live presence, family memory, stories, research, Legacy, Spirals and Pool remain capabilities of a selected Hub or the user's family context.

Messaging / financial boundary
The Connect action is a navigation contract into the existing Community surface. This PR does not invent a parallel Hub messaging or money ledger. Dedicated Hub-to-Hub conversations and cross-pool transfers should be implemented against the existing audited conversation/ledger models rather than introducing a second source of truth.

Database
Adds migration 0063_diaspora_hub_geography.sql. Existing Hub primary keys are preserved, so existing stories/community relationships remain valid.

Validation
Normal repository release/typecheck/browser gates should be run before merge. Railway production remains on the known-good main deployment until this PR is validated and intentionally deployed.
